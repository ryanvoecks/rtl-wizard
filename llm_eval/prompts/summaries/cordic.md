### Design summary

A combined **CORDIC** (COordinate Rotation DIgital Computer) arithmetic engine, providing both vector rotation and rectangular-to-polar conversion in hardware. CORDIC computes trig functions, vector rotations, and magnitude/phase using only shift-and-add operations (no multipliers), making it cheap in FPGA/ASIC logic.

The top wrapper (`cordic_engine`) instantiates two ZipCPU/cordic generated cores that share the same input vector `(i_xval, i_yval)`, clock, clock-enable, and reset:
- **Rotation mode** (`cordic_p2r`): rotates the input vector left by `i_phase`, outputting the rotated `(x, y)`.
- **Vectoring mode** (`cordic_r2p`): reports the **magnitude** and **phase** of the input vector.

Both cores are fully **pipelined** (one result per clock, fixed latency = number of stages). Each works by (1) a *pre-rotation* coarse step mapping the angle/vector into ±45°, (2) a `generate`-unrolled chain of NSTAGES shift-add micro-rotations using a hardcoded `cordic_angle` lookup table (computed offline in C++ since Verilog can't generate these constants), and (3) a round-toward-even output stage. The CORDIC gain (~1.164435) is left uncompensated in the RTL. An **aux/valid bit** is shifted through each pipeline alongside the data (`ax` register) so consumers know when an output is valid. All sequential logic is gated by `i_ce` and clearable by `i_reset`. Parameters are fixed at IW=OW=18 (input/output widths).

### Directory organisation

```
.
└── rtl/
    ├── cordic_engine.v   # top-level wrapper
    ├── cordic_p2r.v      # polar→rectangular core (rotation mode)
    └── cordic_r2p.v      # rectangular→polar core (vectoring mode)
```

### Key modules/files

- **`rtl/cordic_engine.v`** (`cordic_engine`, 56 lines) — Top-level, hand-written wrapper. Declares the public interface and instantiates the two generated cores side-by-side (`u_rot` = `cordic_p2r`, `u_vec` = `cordic_r2p`), wiring the shared `i_xval/i_yval/i_clk/i_ce/i_reset/i_aux` into both. Exposes rotation outputs (`o_rot_xval/yval/aux`) and vectoring outputs (`o_vec_mag/phase/aux`). Parameters: IW=OW=18, ROT_PW=25 (rotation phase width), VEC_PW=26 (vectoring phase width). This is the integration point another agent should start from.

- **`rtl/cordic_p2r.v`** (`cordic_p2r`, 331 lines) — **Rotation core**, polar-to-rectangular. Generated by `gencordic -t p2r -i 18 -o 18`. Working width WW=21, phase width PW=25, **NSTAGES=21**. Takes `i_phase` (angle scaled by 2³²/2π so 2π wraps to 0); pre-rotation uses the top 3 phase bits (`case(i_phase[PW-1:PW-3])`) to fold into ±45°, then 21 shift-add stages drive the phase to zero, rotating `(x,y)` accordingly. Outputs `o_xval/o_yval`.

- **`rtl/cordic_r2p.v`** (`cordic_r2p`, 284 lines) — **Vectoring core**, rectangular-to-polar. Generated by `gencordic -t r2p -i 18 -o 18`. Working width WW=26, phase width PW=26, **NSTAGES=23** (more stages/precision than p2r). Pre-rotation uses the input sign bits (`case({i_xval[IW-1], i_yval[IW-1]})`) to fold into the right quadrant; the 23 shift-add stages drive `y→0`, accumulating the angle into `ph`. Outputs `o_mag` (residual x = magnitude) and `o_phase` (accumulated angle).

**Interaction:** `cordic_engine` is the only module that references the others; the two cores are independent leaf modules with no cross-dependency — they merely consume the same inputs in parallel and produce separate result buses. Both follow an identical internal structure (sign-extend → aux shift-register → pre-rotation `case` → `cordic_angle` table → `generate` CORDIC loop → round-toward-even output), differing only in direction, bit widths, stage count, and the pre-rotation selector. The `cordic_angle` tables and the `// verilator lint_off UNUSED` blocks are generator artifacts — treat the two `.v` cores as regenerated/black-box files and make hand edits in `cordic_engine.v`.
